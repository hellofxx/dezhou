## GitHub 推送完成（沙箱网络限制下的完整方案）
- 结论：仓库 `hellofxx/dezhou` 已建好并推送，Pages 已启用，站点上线 `https://hellofxx.github.io/dezhou/`，部署工作流 success。
- **关键网络限制（重要）**：本机 Bash 沙箱**只放行 `api.github.com:443`，屏蔽 `github.com:443`（git 智能 HTTP 端口）**。因此 `git push` 必失败（Connection reset / timeout），但 GitHub REST API 可用。所有推送走 API。
- **GitHub 连接器是 App 安装令牌**，无 `repo` 创建权限（`create_repository` 返回 403 Resource not accessible by integration），无法建库；需用户 PAT（classic，勾 `repo` + `workflow`）。
- **空仓库 409 坑**：对完全空仓库，`POST /git/blobs` 返回 409 "Git Repository is empty."。解决：先 `PUT /contents/.bootstrap` 激活 `main`，再走 Git Data API。`delete_repo` 权限未授予，无法删库重建。
- **精确复刻提交技巧**：`git cat-file commit <sha>` 取原始对象 → 提取 tree/author/committer(含 unix+tz→ISO)/message（含尾随换行）→ `POST /git/blobs`（逐文件，内容用 `git cat-file blob <sha>` 原始字节 base64）→ `POST /git/trees` → `POST /git/commits`（parents:[]）→ `PATCH /git/refs/heads/main` 带 `force:true`。可使远程 SHA 与本地完全一致（tree_match=True，commit_match 因 7 位缩写 vs 40 位全称误判，实际前缀一致即相等）。
- **部署失败排查**：`build` 作业全过但 `deploy` 作业的 `actions/deploy-pages` 失败——根因是 Pages 源未启用。用 `POST /repos/{owner}/{repo}/pages` 带 `{"build_type":"workflow","source":{"branch":"gh-pages","path":"/"}}` 启用（`build_type:workflow` 即 GitHub Actions 源）。然后 `POST /actions/runs/{id}/rerun` 重跑失败的工作流即可成功。
- **安全**：PAT 仅通过 `-c url."https://$TOKEN@github.com/".insteadOf` 或环境变量注入，从不写入 `.git/config`/文件；部署完成后用户应在 `https://github.com/settings/tokens` Revoke。
- 临时推送脚本用 `Write` 写到项目根 `.ghpush_tmp*.py`，用完 `rm`。注意：无沙箱模式的 Bash 调用会作用在真实 FS 并误删这些文件；后台沙箱模式可正常读取 Write 写入的文件。
